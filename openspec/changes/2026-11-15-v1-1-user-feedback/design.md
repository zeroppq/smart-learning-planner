# Design

## Context

诊断报告（`docs/diagnosis-v1.1.md`）已定位三个缺陷的根因与行号，本设计直接引用其结论。当前实现的关键事实：

- 第一层标准含"与本章其他概念的关系"（`src/lib/agents/coach/standard.ts:18`），题面只问三要素（`src/app/api/coach/start/route.ts:68`）；判定 prompt 传入三层标准全文且无"只按本层"约束，gaps 无白名单校验（`src/lib/agents/coach/service.ts:54-59`）。
- 重判复用 `submitAnswer`，判定成功后答案被清空（`src/app/page.tsx:260`），点击重判因空答案直接 return 不发请求（`page.tsx:215-218`）；后端 `consumeRejudge` 在参数校验之前执行（`src/app/api/coach/judge/route.ts:69-82`）。
- 改时长走"归档目标 + 新建目标"（`src/lib/plans/repository.ts:61-86`），计划挂在旧目标上导致不可见；排期 `perDay = min(3, max(1, ceil(知识点数/14)))` 完全不看时长（`src/lib/agents/planner/schema.ts:140`）。
- 热修 C-4 后 `/api/plans` 对过期 goalId 按当前 active goal 兜底，该行为不得回退。
- 现有 79 项测试用例是回归底线；项目无浏览器自动化依赖，仅有 CDP 测量脚本先例（`scripts/check-mobile.mjs`）。

## Goals / Non-Goals

**Goals:**

- 三个缺陷按已拍板方向修复，判定、重判、改时长三条链路的行为与 spec delta 一致。
- 判定反馈与知识点列表的可读性提升，不损失溯源能力。
- 每个缺陷修复都有页面点击路径的自动化回归。

**Non-Goals:**

- 不做知识点级的差异化预计用时（排期仍按统一基准，预留扩展位）。
- 不修计划生成的模型输出稳定性（引用不存在 ID 偶发整单失败）。
- 不改数据库表结构、不引入新外部服务。
- 不重做视觉风格，只做层次与间距打磨。

## Decisions

### D1 排期算法：时长档位表（待审查确认）

**规则**（替换 `buildDailyTasks` 的 perDay 推导）：

```
每天任务数 perDay = min(3, max(时长档位数, ceil(知识点数 / 14)))
每项预计分钟 = max(15, round(dailyMinutes / 当天实际任务数))
```

时长档位表：

| 每日时长 | 档位数（每天最多新任务） |
|----------|------------------------|
| 10 - 39 分钟 | 1 |
| 40 - 59 分钟 | 2 |
| 60 分钟及以上 | 3 |

`ceil(知识点数/14)` 是 14 天周期的兜底：知识点多而时长短时，保证仍能在 14 天内排完（档位数被抬高），此时每项分钟数用 15 分钟下限兜底。

**40 / 50 / 60 分钟三档边界示例（22 个知识点，ceil(22/14)=2）：**

| 每日时长 | perDay | 总天数 | 每项分钟 | 与 40 分钟档的差异 |
|----------|--------|--------|----------|--------------------|
| 40 | max(2,2)=2 | 11 天 | 20 | 基线（与现状一致） |
| 50 | max(2,2)=2 | 11 天 | 25 | 每项分钟不同，**排期不可区分** |
| 60 | max(3,2)=3 | 8 天 | 20 | 每天多 1 项、总天数缩短 |

上表暴露一个边界问题：**50 分钟落在 40-59 档，与 40 分钟的排期结构完全相同**，不满足 spec"40 与 50 可区分"的场景。两个候选修正（审查时二选一）：

- **方案甲（推荐）**：档位边界改为 10-29 / 30-49 / 50+。40 分钟 → 1 项档但被 14 天兜底抬为 2 项/天（11 天，每项 20 分钟，与现状一致）；50 分钟 → 2 项/天（11 天，每项 25 分钟）——仍然与 40 不可区分，因为兜底把 40 抬到了同一档。**不可行**。
- **方案乙（推荐）**：放弃"档位表"，改用"最小任务粒度 15 分钟"推导：`perDay = min(3, max(ceil(知识点数/14), floor(dailyMinutes / 15)))`。40 → floor(40/15)=2 → 2 项/天、每项 20 分钟、11 天；50 → floor(50/15)=3 → 3 项/天、每项 17 分钟、8 天；60 → floor(60/15)=4 封顶 3 → 3 项/天、每项 20 分钟、8 天。三档两两可区分（40 与 50/60 的天数不同；50 与 60 的每项分钟不同），且规则一条公式说清。

**采用方案乙**：`perDay = min(3, max(ceil(知识点数/14), floor(dailyMinutes/15)))`，每项分钟下限从 5 提到 15。代价是 50 分钟档每项 17 分钟，比 20 分钟基准略碎；换来的是时长真正参与排期且三档可区分。**此规则为提案审查确认项**。

### D2 目标更新：同文本改时长走 UPDATE，schema 零变更

- `POST /api/goals` 增加判断：存在 active goal 且 `goal_text` 与请求一致（trim 后）→ 只更新 `daily_minutes` 与 `updated_at`，保留 `learning_goal_id`；文本不同 → 维持现有"归档 + 新建"（单目标约束不变）。
- schema 影响：**无表结构变更**。`learning_goal` 多一条 UPDATE 路径；`plan` / `daily_task` 查询逻辑不变——active goal 不换 ID，`getCurrentPlanView` 继续命中旧计划，改时长后计划保持可见（修复 C-2）。
- 版本不回退（C-7）：`savePlan` 的版本统计按 `learning_goal_id`（`repository.ts:127-130`），更新路径保留同一 ID，重新生成自然 v1→v2。文本不同的新目标从 v1 开始属"新版本线"，不算回退。
- 改时长后的重排：**不自动重排**。用户在计划页点"按新时长重排"→ 预览确认 → 写入。重排不调用模型（路线不变，仅重算 `buildDailyTasks`），新增轻量接口 `POST /api/plans/rearrange`：`{ confirm: false }` 返回前后对比（每日任务数、总天数、每项分钟、逐日任务预览），`{ confirm: true }` 事务写入并版本 +1。交互复用大调确认框样式。
- 热修 C-4 兼容：`/api/plans` 的 goalId 兜底行为不动；`rearrange` 同样按当前 active goal 操作。

### D3 缺陷A：标准三要素化 + 判定输出带标准编号

- `standard.ts` 第一层标准改为与题面一一对应的三条：①用自己的话说清是什么 ②说明解决什么问题 ③举一个贴近课程的例子。"用自己的话"作为三条的达成质量要求写进判定提示词（照读原文不算达成①），不单列标准条目。"与本章关系"从标准与 gaps 中移除，保留在讲解提示词里，页面归入"建议区"。
- 判定输出格式升级（同时服务 #5 结构化展示）：

  ```json
  {"verdict":"pass|partial|fail","feedback":"...",
   "gaps":[{"standard_index":1,"detail":"具体缺口"}],
   "suggestions":["标准外建议，如与本章的关系"]}
  ```

- `COACH_JUDGE_PROMPT` 增加硬约束：只依据当前层标准判定；`standard_index` 必须是当前层标准条目编号；标准外内容只能写入 suggestions，不得作为不通过理由。
- `validateVerdict` 校验：`standard_index` 越界或缺失的 gap 条目移入 suggestions；gaps 为空数组时 verdict 不得为 partial/fail（反向约束：判不过必须给出对应标准的缺口）。旧格式（纯字符串 gaps）按无编号处理，整体降级为 suggestions，保证解析兼容。
- 前端达标清单 = 本层标准 − gaps 中出现的编号；缺口清单按编号关联标准原文并高亮。

### D4 缺陷B：重判不重填答案 + 次数扣除后置

- 前端：新增 `lastSubmittedAnswer` 状态，每次判定提交成功后保存；重判区块不再显示答案框，明示"基于你上次的回答 + 补充说明重新判定"；重判请求携带 `lastSubmittedAnswer` 与申诉文本。重判区块内增加就地提示与按钮进行中状态（局部 state，不用页面顶部 notice）。
- 后端顺序调整：参数校验（note ≥ 2、answer 非空）→ 模型调用 → 成功后在同一 SQLite 事务内执行 `consumeRejudge`（`UPDATE ... WHERE rejudge_used = 0`，changes=0 则回滚并返回"已用完"）与 `recordLayerResult`。模型调用不放进事务（避免长事务）。校验失败、模型失败均不扣次数（Q3 选 A）。单用户场景下并发风险可忽略，事务内条件更新保证不超扣。
- "重判为最终结果"语义不变：重判后仍允许普通重提（不消耗次数）。

### D5 #2 可读性：引用角标化与列表卡片化

- 讲解/答疑文本渲染时用正则把 `【文档名 第N段】` 替换为角标组件（上标小标签），点击展开出处卡片（文档名、段落序号、定位到段落）。数据层原文不动——来源标注能力保留，仅改展示形态（硬约束）。
- 知识库页知识点列表改为卡片：标题 + 摘要（`paragraph_text` 前 50 字）+ 展开查看详情与出处。

### D6 页面点击路径回归：CDP 轻量脚本

- 不引入 Playwright（新依赖 + 浏览器下载，超出 3-4 天预算的风险源）。复用 `check-mobile.mjs` 的 CDP 模式，新增 `scripts/verify-ui-paths.mjs`：无头 Edge/Chrome 打开页面，按"判定不过 → 填申诉 → 点申请重判 → 断言请求发出与就地反馈"等路径执行点击与 DOM 断言。
- 三个缺陷各至少一条点击路径用例；接口脚本保留，但验收以点击路径为准。

### D7 视觉打磨（#1）范围与裁剪顺序

四页统一间距与标题层次、判定卡与重判区块的重点突出、缺口高亮样式。若时间超出，裁剪顺序：先砍进度页 → 再砍知识库页 → 保今日学习页与计划页（得分链路主画面）。

## Risks / Trade-offs

- [50 分钟档每项 17 分钟，学习颗粒偏碎] → design 已列为审查确认项；若不接受，退回方案甲并放宽 spec"40 与 50 可区分"场景为"40 与 60 可区分"。
- [判定输出格式升级后模型不遵守编号] → `validateVerdict` 做降级兼容（无编号 gap 转 suggestions），最坏情况退化为现状行为，不会误判。
- [goal_text 相同但用户意图是"重新开始"] → 更新路径只改时长不改文本；想重来的用户会改目标文本，自然走归档路径。文档写明。
- [CDP 脚本对 Windows 无头浏览器路径的依赖] → 脚本启动失败时给出中文提示与手工点击清单兜底，不阻塞验收。
- [改排期后已有演示数据（40 分钟、11 天 2 项）变化] → 方案乙下 40 分钟结果与现状完全一致，演示数据不受影响。

## Migration Plan

- 本地 SQLite，无部署迁移；`learning_goal` 更新路径对存量数据兼容（active goal 不变，仅新增 UPDATE 分支）。
- 回滚策略：各组独立提交，出问题按组 revert；不涉及数据回滚（更新路径不破坏旧记录）。
- 回归底线：79 项用例只增不减；热修 C-4 行为（旧 goalId 不 409）在 `/api/plans` 与 `rearrange` 均保留兜底，并有测试锁定。

## Open Questions

- CDP 点击脚本若在本机不稳定，是否允许引入 Playwright 作为替代（仅在此前提下）。
