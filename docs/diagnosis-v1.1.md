## 二、缺陷 A：第一层判定依据越界

### 2.1 复现步骤（demo 基线，真实模型）

1. `node --experimental-strip-types scripts/reset-demo.mjs fresh`，得到 22 个知识点、40 分钟、计划 v1。
2. 取路线第 1 个知识点 `1.1 计算机的本质：把规则变成动作`，调用 `POST /api/coach/start`。
3. 页面展示的第一层题目为：

   > 请用你自己的话讲清楚「1.1 计算机的本质：把规则变成动作」是什么、解决什么问题，并举一个例子。

4. 提交一段**只覆盖题面三要素**的回答（是什么、解决什么问题、微波炉例子），不提本章其他概念。
5. 调用 `POST /api/coach/judge` 判定。

### 2.2 复现结果（3 个知识点，3/3 一致）

| 知识点 | 回答覆盖 | 判定 | gaps |
|--------|----------|------|------|
| 1.1 计算机的本质 | 是什么 + 解决什么问题 + 微波炉例子 | `partial` | “未说明与第一章「计算机是什么：从算盘到芯片」中其他概念的关系” |
| 1.3 冯·诺依曼架构 | 是什么 + 解决什么问题 + 菜谱例子 | `partial` | ① 与第一章承接关系缺失；② “重新接线”未对应早期机器；③ 例子未讲“指令与数据形式相同、位置相邻” |
| 1.4 硬件五大家族 | 是什么 + 解决什么问题 + 厨房例子 | `partial` | “未说明与第一章「计算机是什么：从算盘到芯片」中其他概念的关系” |

第 1.3 条的第 ③ 个 gap 尤其能说明问题：它要求回答讲解里的“副作用”细节，而这条既不在题目里，也不在第一层标准清单里，属于标准外缺口。

同时实测演示脚本第 4 段的含糊答案（“大概就是那个意思吧，我也说不太清楚。”）在 1.5、2.1 两个知识点上 **2/2 判 `fail`**，演示文案“未通过”成立。

### 2.3 根因（带文件与行号）

| 编号 | 根因 | 位置 | 说明 |
|------|------|------|------|
| A-1 | 第一层标准本身超出题面 | `src/lib/agents/coach/standard.ts:18` | 标准第 2 条为“能说明它与${chapter}其他概念的关系”，而题目只问“是什么、解决什么问题、举例”（`src/app/api/coach/start/route.ts:68`） |
| A-2 | 判定时传入三层标准全文，未限制“只按本层” | `src/lib/agents/coach/standard.ts:36-43`、`src/app/api/coach/judge/route.ts:66-67,139` | `formatStandardForPrompt` 把讲清楚/做对题/做出来三套标准全部拼进 prompt；判定 prompt 只标了“当前判定层”（`src/lib/agents/coach/system-prompt.ts:124-125`），没有“只依据本层”的硬约束 |
| A-3 | 判定提示词没有“标准外只能建议”的约束 | `src/lib/agents/coach/system-prompt.ts:40-49` | 规则只有“gaps 列出没达到的标准条目”，未要求 gap 必须逐条引用本层标准原文，也未禁止把讲解细节、其他层要求写进 gaps |
| A-4 | gaps 生成逻辑没有标准白名单校验 | `src/lib/agents/coach/service.ts:54-59` | `validateVerdict` 只做“非空字符串 + 最多 5 条”，不与本层标准比对，标准外缺口可以原样落到前端 |
| A-5 | 讲解内容与判定依据混在一起 | `src/lib/agents/coach/system-prompt.ts:21-28`、`src/app/page.tsx:477-482` | 讲解里生成“和本章的关系”段落，页面上紧挨着判定标准展示；用户自然以为这是判定要求，而题面并没有问 |

### 2.4 回答任务中的四个问题

1. **第一层“讲清楚”的判定依据是什么？** 见 `standard.ts:16-20`：是什么/解决什么问题、与本章其他概念的关系、被追问时不含糊。
2. **是否混入了超出本层标准的要求？** 是，但更准确地说有两层问题：其一，“与本章关系”本身就是标准条目，却不在题面里；其二，模型还会把讲解里的机制细节（如 1.3 的“指令与数据形式相同”）当作 gap，这部分连标准清单都没有。
3. **缺口字段是否限定在本层标准清单内？** 否。后端没有任何白名单或映射校验，模型给什么就展示什么。
4. **是否需要增加“只依据本层前置展示标准判定，标准外内容只能作为建议、不得作为不通过理由”的硬约束？** **需要，且必须与标准清单同步改**。只改提示词而保留 `standard.ts:18`，模型仍会把“与本章关系”当成必过项；只改标准而不约束 gaps，模型仍可能把讲解细节当缺口。

### 2.5 为什么当时没发现（对照组 4 验收）

`docs/evidence/recordings/2026-11-14-group-4-issues.md:30` 的真实调用样例里，当时就把“完整复述讲解内容 → 部分通过 → 讲清了内容，但没说明与本章其他概念的关系”当作**正确判定**记录，而不是识别为“题面没要求”。任务 4.4 的验收口径只有“含糊复述被判未通过并指出缺口”，没有“符合题面三要素的回答应通过”这一条；验证脚本 `scripts/verify-coach.mjs:41` 又把讲解全文加上“能帮助理解后续章节”直接当答案，天然覆盖了“本章关系”，所以永远测不到越界。

### 2.6 修复方向建议（不写代码）

1. 产品口径先拍板：第一层到底考“是什么 + 解决什么问题 + 举例”，还是也考“与本章关系”。
2. 若保留“本章关系”：题目必须显式问出来；标准与题面一一对应。
3. 若降为建议：`standard.ts` 第一层只保留题面三要素，把“本章关系”移到讲解或建议区。
4. 判定侧加硬约束：只依据当前层标准判定；标准外内容只能作为“建议”，不得进入 gaps、不得作为不通过理由；gaps 必须逐条对应本层标准原文。
5. 校验侧兜底：`validateVerdict` 增加“gaps 只能来自本层标准”的过滤，标准外条目降级为 feedback 中的建议。
6. 回归用例：新增“符合题面三要素、不提本章关系 → pass”与“提及标准外细节 → 不得因此 partial”两条真实调用用例。

## 三、缺陷 B：申请重判按钮点击无反应

### 3.1 复现步骤与结果

前端真实路径（代码级确定，`src/app/page.tsx`）：

1. 第一层提交后判 `partial`。
2. 判定成功分支执行 `setAnswer("")`（`page.tsx:260`）与 `setRejudgeNote("")`（`page.tsx:261`），**答案框被清空**。
3. 页面出现“申请重判（只能一次）”区块（`page.tsx:561-580`），用户填写申诉文本，按钮变为可点（`disabled` 只校验申诉文本长度，`page.tsx:574`）。
4. 点击按钮调用 `submitAnswer({ rejudge: true })`（`page.tsx:573`）。
5. `submitAnswer` 第一段先校验 `answer.trim().length === 0`（`page.tsx:215-218`），此时答案已空 → `setNotice("先写下你的回答，再提交判定。")` 后 `return`，**没有发出任何网络请求**。
6. 提示显示在页面顶部第一张卡片（`page.tsx:458-460`），而重判区块在下方判定卡内，用户看不到，表现就是“点了没反应”。

接口侧实测（真实模型）：

| 场景 | 结果 | 副作用 |
|------|------|--------|
| 1.2 先判 `fail`，再发 `answer=""` + `rejudge=true` | HTTP 400「请先作答再提交判定。」 | **`rejudge_used` 已从 0 变 1，次数被吞** |
| 1.1 先判 `partial`，再发正常答案 + 申诉 | HTTP 200，仍 `partial` | 接口本身可用，次数正常消耗 |
| 1.1 紧接着第二次重判 | HTTP 400「该知识点的重判机会已用完。」 | 符合规格 |

结论：重判接口没坏，坏的是前端调用链；后端还存在“先扣次数、后校验”的状态机缺陷，会让无效请求或模型失败也烧掉唯一一次机会。

### 3.2 根因（带文件与行号）

| 编号 | 根因 | 位置 | 说明 |
|------|------|------|------|
| B-1 | 判定成功后清空答案 | `src/app/page.tsx:260` | 重判复用了同一个 `answer` 状态，但原答案已被清空 |
| B-2 | 重判前置校验复用“提交判定”的答案检查 | `src/app/page.tsx:215-218` | 空答案直接 `return`，请求根本没发出 |
| B-3 | 反馈位置离操作点太远 | `src/app/page.tsx:458-460`、`page.tsx:561-580` | 提示在顶部卡片，重判在下方；视觉上等于无反应 |
| B-4 | 后端先消耗次数、后校验参数 | `src/app/api/coach/judge/route.ts:69-82` 与 `:85,:121-123` | `consumeRejudge` 在 note 长度、question、answer 校验之前执行 |
| B-5 | 次数消耗是“直接置 1”，无回滚 | `src/lib/agents/coach/repository.ts:121-132` | `UPDATE ... SET rejudge_used = 1`；模型调用失败（`route.ts:143-157`）也不返还 |
| B-6 | 前端没有重判进行中状态与就地错误 | `src/app/page.tsx:571-578` | 按钮只有 `disabled`，无 loading/错误文案，用户无法判断请求是否发出 |

### 3.3 对照任务 4.7 当时的验证路径，为什么没发现

- 4.7 验收项（`openspec/changes/archive/2026-11-14-build-competition-mvp/tasks.md:42`）写的是“实现判定标准前置展示、掌握状态写入与重判一次，验证第二次重判被拒绝”。
- 实际验证走的是纯接口脚本 `scripts/verify-coach.mjs:102-131`：按 STEP 6 直接构造“先 fail → 再带 `answer` + `rejudgeNote` 调接口 → 再调一次”，全程绕过页面。
- 规格走查 LS-18/LS-19（`docs/spec-walkthrough.md:76-77`）同样以 `consumeRejudge` 和接口 400 为观察点，判定“通过”。
- 因此当时验证的是**接口语义**，用户踩的是**页面交互**：前端清空答案导致请求不发出，脚本里永远不会出现空答案。验收口径缺一条“从页面点击按钮”的路径。

### 3.4 修复方向建议（不写代码）

1. 重判时复用上一次提交的答案（保存 `lastSubmittedAnswer`），不再要求用户重填答案；申诉文本只作为补充上下文。
2. 或判定成功后不清空答案，只清空申诉文本；重判按钮直接提交当前答案 + 申诉。
3. 后端把重判次数消耗放到全部参数校验通过之后，并与判定调用放在同一事务边界；模型失败不扣次数，返回剩余次数。
4. 提示就地显示在重判区块内，按钮增加进行中状态，禁止重复点击。
5. 回归用例补充“页面点击路径”：判定不过 → 填申诉 → 点击 → 必须产生请求；以及“空答案 + 重判”不得消耗次数。

## 四、缺陷 C：修改每日时间后计划不变

### 4.1 复现步骤与实测数字

**现场库证据（诊断开始时的真实状态）：**

| 对象 | 实测值 |
|------|--------|
| `learning_goal` | 旧目标 40 分钟（archived）、新目标 50 分钟（active） |
| `plan` | 只有 1 份 v1，挂在**旧 40 分钟目标**上 |
| `daily_task` | 22 条，`estimated_minutes` **全部 20** |
| `GET /api/plans/current` | `{ ok: true, plan: null }` |

即：用户改完时间后，旧计划被挂到已归档目标上，当前活跃目标没有计划，页面刷新后显示“还没有学习计划”。

**基线复现（fresh，40 分钟）：**

1. `reset-demo fresh` → 22 个知识点、22 条任务、每任务 20 分钟、日期 2026-11-15 → 2026-11-25。
2. `POST /api/goals` 把时长改为 50 → 返回新目标，澄清问题 2 条。
3. `GET /api/plans/current` → **`plan: null`**（旧计划立即从页面消失）。
4. 用旧目标 ID 调 `POST /api/plans` → **409「目标已变化，请刷新页面后重新生成。」**
5. 用新目标 ID 重新生成 → 200，计划 **v1**，每任务 **25 分钟**，日期仍为 2026-11-15 → 2026-11-25，任务数仍 22。

结论：

- 时长参数**确实传到了**每日任务生成（20 → 25 分钟），不是完全没生效。
- 但“每天几项、排到哪一天”完全由知识点数量与 14 天周期决定，时长不参与；所以 40 → 50 后，页面上的任务条数、日期、路线顺序一模一样，只有每条小字从 20 变 25，用户感知就是“计划完全没变”。
- 更严重的是：改时间会归档旧目标，旧计划随之不可见；刷新后不是“计划没变”，而是“计划没了”。
- 计划版本还会从 v1 重新开始（新目标没有历史版本），与演示里“v1 → v2”的版本叙事不是同一套账。

### 4.2 根因（带文件与行号）

| 编号 | 根因 | 位置 | 说明 |
|------|------|------|------|
| C-1 | 改时间 = 归档旧目标 + 新建目标 | `src/app/api/goals/route.ts:33`、`src/lib/plans/repository.ts:61-86` | `createOrReplaceActiveGoal` 无条件归档当前目标，计划仍挂在旧目标上 |
| C-2 | 当前计划只按“活跃目标”查 | `src/lib/plans/repository.ts:184-206` | `getCurrentPlanView` 用 active goal 查 plan；新目标没有 plan → 返回 `undefined`，进度页同样变空（`src/lib/plans/progress.ts:48-52`） |
| C-3 | “目标已变化”的触发条件 | `src/app/api/plans/route.ts:37-42` | 请求里的 `goalId` 与当前 active goal 不一致就 409 |
| C-4 | 前端用旧视图里的目标 ID 生成 | `src/app/plan/page.tsx:132-137`、`:243` | `submitClarify` 与“按默认直接生成”都用 `view?.goal.learning_goal_id`；`startPlanning` 刚创建的新目标 ID 没有保存到视图，必然 409 |
| C-5 | 每日任务分配不看时长 | `src/lib/agents/planner/schema.ts:140` | `perDay = min(3, max(1, ceil(route.length / 14)))`，只由知识点数和 14 天决定 |
| C-6 | 时长只影响“每项分钟数” | `src/lib/agents/planner/schema.ts:146` | `minutes = max(5, round(dailyMinutes / tasksToday))`；22 点 → 每天 2 项 → 40/2=20、50/2=25 |
| C-7 | 版本号按目标重新计 | `src/lib/plans/repository.ts:127-130` | `MAX(plan_version) WHERE learning_goal_id = 新目标` → 从 1 开始 |

**“每任务 20 分钟是不是写死？”** 不是业务写死。`src/lib/db.ts:69` 的 `DEFAULT 20` 只是建表默认值；实际分钟数按 `dailyMinutes / 当天任务数` 均分（`schema.ts:146`）。真正“写死”的是“每天几项”的推导方式。

### 4.3 顺带核查两项

**① 文案“每页 40 分钟”**

- 当前代码三处均为“每天”：`src/app/plan/page.tsx:310`、`src/app/page.tsx:417`、`src/app/progress/page.tsx:169`。
- 全仓检索“每页”无结果；`git log --all -S "每页"` 也无历史记录。
- 结论：**未复现**，当前版本没有这个错别字；可能是用户转述或旧截图记忆。无需修复。

**② 澄清问题里的“29 个知识点”**

- 诊断开始时的库中确实有 **29 个知识点**：预置讲义 22 个 + 用户上传《中国近代史.txt》切出 7 个（共 29）。
- 澄清提示词只注入一个数字（`src/lib/agents/planner/system-prompt.ts:45-53`，调用处 `src/app/api/goals/route.ts:34-40`），没有注入课程名或知识点清单。
- 实测当前 22 个知识点时，模型返回“期末考试的范围是否就是知识库里这 22 个知识点”，**数字与库一致，不是编造**。
- 结论：用户看到的“29 个”来自真实计数，不是模型幻觉；但提示词把“库里知识点数量”直接等同于“这门课的范围”，在多资料场景会让模型混淆两门课。建议注入“课程名 + 每门课数量”，并让澄清问题明确指向主资料。

### 4.4 为什么当时没发现（对照规格走查）

`docs/spec-walkthrough.md:42` 的 LP-2“修改每日时长”判定为**通过**，观察口径是“改为 60 后，任务预计用时按 60 分配”。实现确实满足这句话（60 → 每项 30 分钟），所以走查通过；但没有验证“每日任务数量/日期是否变化”，也没有验证“改完刷新后旧计划是否还在”。任务 4.x 的单元测试同样只断言“每小时段合计接近每日时长”（`src/lib/agents/planner/schema.test.ts:121-135`），不涉及排期变化与目标切换。

### 4.5 修复方向建议（不写代码）

1. **目标更新而不是目标替换**：改时长时更新当前 active goal 的 `daily_minutes`，保留同一目标与同一计划版本线；或新建目标后自动把旧计划迁移并重排。
2. **前端用新目标 ID**：`startPlanning` 成功后就地保存返回的 goal，澄清与“按默认直接生成”使用它；生成前也可重新拉一次 `/api/plans/current`，避免 409。
3. **让时长参与排期**：例如按“单项 20~30 分钟”估算每天项数，再与 14 天上限取小；这样 40 → 50 会改变每天项数或总天数。具体口径需用户拍板（见 6.1）。
4. **明确用户预期**：若产品决定“时长只影响每项预计用时”，页面必须写清“每日任务条数由知识点数量决定”，避免误解。
5. 版本号：若保留“改时间为新目标”，至少不要把版本重置说成“计划未变”；若改为更新目标，版本可正常递增。

### 5.1 逐项判定

### 5.2 单项结论

1. **缺陷 A 不在演示主线。** 脚本第 4 段故意答含糊，稳定判未通过；但若现场评委要求“答一个正确的试试”，就会踩标准外依据，属于“演示可控、临场不可控”。
2. **缺陷 B 不在演示主线。** 脚本不点“申请重判”。demo 数据下若现场进入第二层并判不过，重判区块会出现且按钮可点，但点击不会发请求；建议现场不要演示重判，v1.1 修复后再开放。
3. **缺陷 C 不在演示主线。** 脚本不改每日时间。但同源的“已有计划再点开始规划 → 按默认直接生成 = 409”会影响 **demo 模式彩排/重演示**（`reset-demo demo` 后从第 2 段开始）。正式录制按脚本用 `fresh` 则不受影响。
4. **是否需在 main 热修（待用户确认）：** 建议只把“C-4 旧 goalId 409”作为候选。它冻结令下属于“影响演示正确性”，改动面小（前端取新 goalId 或后端按最新 active goal 兜底）。缺陷 A、B 不进 main，留到 v1.1。
